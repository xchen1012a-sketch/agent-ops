# 前后端与数据库开发顺序

## 结论

本项目不采用“完整后端全部做完再做前端”，也不采用“前端先按数据库字段自由Mock”。采用：

> 领域与契约先行，后端基础先行，前端基于OpenAPI Mock并行，按垂直切片联调。

由于三个项目包含Agent状态、MySQL权限、SQL安全和外部服务，整体节奏应偏后端主导。

## 阶段顺序

### 1. 业务与验收先确认

确认用例、角色、权限、数据生命周期、Agent节点、异常和验收样本。此时不写代码。

### 2. 同步设计三份契约

- 领域/数据库逻辑模型：实体、关系、唯一性、生命周期和索引需求。
- API/OpenAPI契约：前端真正依赖的请求、响应、错误和SSE事件。
- Agent契约：State、节点I/O、工具Schema、重试、幂等和checkpoint。

数据库字段不是前端契约。前端只依赖API DTO；物理表字段可在不破坏API的情况下演进。

### 3. 后端工程基础先搭

先完成FastAPI应用壳、配置、错误、日志、健康检查、数据库连接、Alembic、鉴权骨架和OpenAPI stub。只实现一个最小垂直切片，不一次搭完整业务。

### 4. 前端基于契约Mock并行

OpenAPI冻结后生成/校验TypeScript类型和Mock响应，搭建Vue App Shell、三菜单、加载/空/错误状态。Mock必须由契约驱动，禁止手写与后端脱节的字段。

### 5. 按垂直切片交付

每个切片依次完成：迁移 → repository → use case → LangGraph node/graph → API → 前端页面 → 契约/E2E。优先顺序：

1. 身份与会话公共体验。
2. 法律咨询最小问答闭环。
3. 招聘材料解析与报告闭环。
4. 智能问数一条安全查询闭环。
5. 流式、重试、导出、飞书和高级功能。

### 6. 联调与回归

前端从Mock切换真实API；契约测试阻止字段漂移；数据库迁移、权限、安全、Agent轨迹和E2E共同验收。

## 为什么不直接前端先行

- 前端若直接围绕数据库字段Mock，会把物理存储泄漏为公开契约。
- Agent错误、运行状态、SSE和权限需要后端先定义语义。
- 智能问数的SQL安全与双数据库权限不能由前端原型决定。

## 为什么不等待完整后端

- OpenAPI稳定后，前端可提前验证信息架构、交互和视觉。
- Mock可尽早发现响应结构、分页、错误和流式事件不合理。
- 垂直切片能更早形成可演示成果并降低大批量联调风险。
