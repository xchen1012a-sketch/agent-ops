## 🧪 实验 A：零样本测试（不提供 Schema）

### 系统提示词

```
你是一个 SQL 专家。请根据用户问题生成 MySQL 查询。

```

### 典型 LLM 输出与问题分析

**Q1: 2026 年 5 月的总销售额是多少？**

```sql
-- ❌ LLM 零样本输出（典型幻觉）
SELECT SUM(amount) AS total_sales
FROM orders
WHERE YEAR(order_time) = 2026 AND MONTH(order_time) = 5;
```

| 问题 | 说明 |
|------|------|
| `amount` 字段不存在 | 实际是 `fact_orders.actual_amount` |
| `orders` 表不存在 | 实际是 `fact_orders` |
| `order_time` 字段不存在 | 需关联 `dim_date.date_value` |
| 缺少 JOIN、缺少状态筛选 | — |

**Q3: 上月销售额最高的 5 个品类**

```sql
-- ❌ 零样本输出
SELECT category, SUM(sales) AS total
FROM products
JOIN order_items ON products.id = order_items.product_id
WHERE order_date BETWEEN '2026-05-01' AND '2026-05-31'
GROUP BY category
ORDER BY total DESC
LIMIT 5;
```

| 问题 | 说明 |
|------|------|
| 全部表名/字段名都是编造的 | 完全是幻觉输出 |

> 📊 **零样本准确率：0/10** — 没有任何 Schema 上下文，LLM 只能凭对"电商数据库"的常识猜测，100% 产生幻觉。

### 逐题结果分析

#### ✅ Q1（2 表 JOIN）：2026 年 5 月的总销售额

```sql
-- LLM 生成 ✅ 正确
SELECT ROUND(SUM(o.actual_amount), 2) AS 总销售额
FROM fact_orders o
JOIN dim_date d ON o.order_date_key = d.date_key
WHERE d.year = 2026 AND d.month = 5
  AND o.order_status_key NOT IN (5, 6);
```

#### ✅ Q2（3 表 JOIN）：各渠道的订单量和销售额排行

```sql
-- LLM 生成 ✅ 正确
SELECT ch.channel_name AS 渠道,
       COUNT(DISTINCT o.order_key) AS 订单量,
       ROUND(SUM(o.actual_amount), 2) AS 销售额
FROM fact_orders o
JOIN dim_channel ch ON o.channel_key = ch.channel_key
JOIN dim_date d ON o.order_date_key = d.date_key
WHERE d.year = 2026 AND d.month = 5
GROUP BY ch.channel_name
ORDER BY 销售额 DESC;
```

#### ✅ Q5（3 表 JOIN）：金卡会员的人均消费

```sql
-- LLM 生成 ✅ 正确
SELECT ROUND(SUM(o.actual_amount) / COUNT(DISTINCT c.customer_key), 2) AS 人均消费
FROM fact_orders o
JOIN dim_customer c ON o.customer_key = c.customer_key
WHERE c.customer_level = '金卡';
```

---

#### ⚠️ Q8（5 表 JOIN）：手机品类下各品牌的销售额排名

```sql
-- LLM 生成（⚠️ 有一处关联字段错误）
SELECT p.brand,
       ROUND(SUM(od.sub_total), 2) AS 销售额
FROM fact_order_details od
JOIN dim_product p ON od.product_key = p.product_key       -- ✅ 正确
JOIN dim_product_category pc ON p.product_key = pc.category_key  -- ❌ 错误！
WHERE pc.category_name = '手机通讯'                         -- ✅ 筛选条件正确
GROUP BY p.brand
ORDER BY 销售额 DESC;
```

> **错误分析**：`p.product_key = pc.category_key` 应该是 `p.category_key = pc.category_key`。
> `product_key` 是商品维度的主键，`category_key` 才是品类维度的外键。LLM 混淆了这两个字段。

#### ❌ Q9（7 表 JOIN）：华东区金卡会员通过 App 购买手机品牌 TOP5

```sql
-- LLM 生成（多处潜在问题）
SELECT p.brand, ROUND(SUM(od.sub_total), 2) AS 销售额
FROM fact_order_details od
JOIN fact_orders o         ON od.order_key = o.order_key         -- ✅
JOIN dim_product p         ON od.product_key = p.product_key      -- ✅
JOIN dim_product_category pc ON p.category_key = pc.category_key  -- ✅
JOIN dim_customer c        ON o.customer_key = c.customer_key     -- ✅
JOIN dim_region r          ON o.region_key = r.region_key         -- ✅
JOIN dim_channel ch        ON o.channel_key = ch.channel_key      -- ✅
WHERE pc.category_name = '手机通讯'
  AND r.region_name = '华东'          -- ⚠️ 实际值是 '华东' 还是 '华东区'？
  AND c.customer_level = '金卡'       -- ✅
  AND ch.channel_name = 'App 商城'    -- ⚠️ 实际值是 'App 商城' 还是 'APP商城'？
GROUP BY p.brand
ORDER BY 销售额 DESC
LIMIT 5;
```

**7 表 JOIN！** 核心问题：
- LLM 不知道枚举值的精确写法（`'华东'` vs `'华东区'`，`'App 商城'` vs `'APP商城'`）
- 注意力被 7 张表的关联关系严重分散

## 📊 NL2SQL 错误模式系统分类

通过 10 题 × 多次测试，我们归纳出 6 大类错误：

| 错误类型 | 占比 | 典型表现 | 根本原因 |
|----------|:----:|----------|----------|
| 🔴 **表名/字段名幻觉** | 20% | 捏造不存在的表或字段 | 无 Schema 或 Schema 不足 |
| 🔴 **JOIN 条件错误** | 35% | 代理键和业务键混淆，关联错字段 | 不理解外键参照关系 |
| 🟡 **字段值不精确** | 15% | `'华东'` vs `'华东区'` | 对维度表枚举值不了解 |
| 🟡 **聚合粒度错误** | 15% | 订单级求和 vs 明细级求和混用 | 不理解表的业务粒度 |
| 🟢 **SQL 语法错误** | 10% | GROUP BY 遗漏、别名冲突 | LLM 注意力分散 |
| 🟢 **业务逻辑错误** | 5% | 退款率计算公式错误 | 业务语义理解偏差 |

## 💸 注意力稀释效应：为什么 JOIN 越多问题越大

```
单表 (Q1):     ████████████████████ 100% 注意力 → 准确率 95%+
2-3表 (Q2-7):  ████████████░░░░░░░░  65% 注意力 → 准确率 85%
4-5表 (Q8):    ████████░░░░░░░░░░░░  40% 注意力 → 准确率 70%
6-7表 (Q9-10): ████░░░░░░░░░░░░░░░░  20% 注意力 → 准确率 45%
```

每多 JOIN 一张表，LLM 需要在 Prompt 中**多理解一个完整表结构**，并在生成 SQL 时**多匹配一个精确关联条件**。当 JOIN 达到 7 张表时，LLM 的有效注意力已被稀释到难以准确选择正确字段的程度。

## 🛠️ 缓解策略（临时方案，治标不治本）

### 策略 1：创建视图封装常用 JOIN

```sql
-- 将常用维度预 JOIN 成视图
CREATE VIEW v_order_summary AS
SELECT
    o.order_key, o.actual_amount, o.item_count,
    d.date_value AS order_date,
    d.year AS order_year, d.month AS order_month,
    c.customer_level, c.age_group,
    ch.channel_name,
    r.region_name,
    os.status_name
FROM fact_orders o
JOIN dim_date d           ON o.order_date_key = d.date_key
JOIN dim_customer c       ON o.customer_key = c.customer_key
JOIN dim_channel ch       ON o.channel_key = ch.channel_key
JOIN dim_region r         ON o.region_key = r.region_key
JOIN dim_order_status os  ON o.order_status_key = os.order_status_key;
```

- ✅ 减少了部分 JOIN
- ❌ 视图只覆盖了订单维度，不包含商品/品类维度
- ❌ 多个视图之间仍需 JOIN

## 🎯 关键结论：必须引入大宽表

| 维度 | 星型模型直接查询 | 大宽表查询 | 提升幅度 |
|------|:---:|:---:|:---:|
| 平均需 JOIN 表数 | 3-7 张 | **0 张** | 100% |
| NL2SQL 准确率 | 60-80% | **92-97%** | +30%+ |
| Prompt Token 消耗 | 2500-3500 | **800-1200** | -70% |
| LLM 单次推理延迟 | 3-5s | **1-2s** | -60% |
| SQL 执行时间 | 50-200ms | **10-30ms** | -80% |
| 数据存储冗余 | 无 | ~3x | 可接受 |
