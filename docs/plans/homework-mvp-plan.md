# 大数据应用实训 MVP 项目计划书

## 1. 结论

当前系统已经明显超过作业标准：它不是课程示例里的单模块 Demo，而是一个 Vue 3 + FastAPI + MySQL + 三个 Agent 服务的企业级多智能体平台雏形。继续按完整企业级路线推进，成本会很高，也会把精力消耗在作业评分不直接需要的功能上。

MVP 应该收敛为“可演示、可截图、可写报告”的三模块项目：

- 模块一：AI 法律咨询系统，保留法律咨询主链路。
- 模块二：工作流智能体，使用现有智能招聘 Agent 承担 Dify 工作流案例角色。
- 模块三：智能问数系统，保留自然语言问数、SQL 展示、结果表格/图表主链路。

本 MVP 不追求生产级 RAG、完整权限治理、全量审计与运维体系。Dify、飞书/企业微信、MCP 不能完全删除，因为它们是作业标准中的显性展示点；MVP 的处理方式是保留“最小可展示闭环”，砍掉生产级复杂度。

## 2. 作业完成标准摘要

根据 `docs/homework/` 中的实训报告大纲和课件，最终报告需要围绕三个模块展开：

| 模块 | 作业标准要求 | MVP 交付方式 |
| --- | --- | --- |
| AI 编程实战 | AI 法律咨询系统、系统架构、核心代码、测试截图、运行截图、问题记录 | 用当前法律咨询 Agent + Web 页面完成咨询、历史、报告/配置截图 |
| Dify 工作流智能体开发 | 工作流总览、节点配置、综合案例、成果截图、DSL 或工作流证据 | 用智能招聘 Agent 作为“工作流智能体”案例，同时保留 Dify 工作流截图/DSL 证据 |
| 智能问数系统实战 | MySQL 数据模型、大宽表、NL2SQL Prompt、企业微信/飞书集成、端到端问答截图 | 用智能问数 Agent 完成自然语言问题到 SQL/结果展示，并保留最小飞书/企微入口截图 |

评分重点不是系统多复杂，而是：

- 三个模块都有可运行交付物。
- 报告中有架构图、关键代码、截图和问题记录。
- 演示时链路完整可用。
- 有一定创新扩展，但不能让扩展功能拖垮主线。

## 3. 当前系统与作业标准对比

| 对比项 | 作业原标准 | 当前系统 | MVP 判断 |
| --- | --- | --- | --- |
| 前端 | HTML/CSS/JS 或基础页面 | Vue 3 + Element Plus 统一工作台 | 保留，作为升级亮点 |
| 后端 | Node.js/Express、SQLite 示例 | FastAPI + MySQL + 三个 Agent API | 保留，但只演示必要接口 |
| 法律咨询 | 聊天、历史、配置、AI 回答 | 已有法律咨询 Agent 和页面 | MVP 主链路 |
| Dify 工作流 | Dify 节点、DSL、案例 | 当前更偏自研工作流/Agent | 运行主链路可用招聘 Agent，报告证据必须保留 Dify 工作流图/DSL 或等价截图 |
| 智能问数 | Dify + MCP + MySQL + 飞书/企微 | 已有智能问数 Agent、SQL 审计、Feishu event 接口痕迹 | 保留 Web 端问数，同时保留飞书/企微最小入口和配置截图 |
| API 配置 | 课程未强要求统一配置 | 系统已有 API 配置中心 | 保留，解决每账号独立 API Key 的产品亮点 |
| 运维部署 | 本地运行即可 | Nginx/Ops/多服务部署规划 | MVP 只保留本地启动和健康检查 |

## 4. MVP 保留范围

### 4.1 统一工作台

必须保留：

- 登录或本地管理员入口。
- 左侧导航进入三个模块。
- 系统 API 配置页。
- 每个账号独立 API Key 配置的设计说明。
- 三个 Agent 的健康状态或最小可用检查。

不追求：

- 完整多租户权限体系。
- 复杂组织、角色、菜单授权。
- 生产级密钥轮换、审计和告警。

### 4.2 法律咨询 Agent

必须保留：

- 发起法律咨询。
- 展示 AI 回复。
- 展示咨询历史。
- 至少一张结果/报告类页面截图。
- API Key 未配置时有清晰提示或降级响应。

可以去掉或降级：

- Qdrant 向量库。
- BGE Embedding。
- Reranker。
- 复杂法律知识库导入。
- 高风险人工审核流。
- PDF/DOCX 报告导出。

MVP 判断：法律咨询只要能完成“用户提问 -> 系统回答 -> 保存记录 -> 截图进报告”，就满足作业主线。

### 4.3 智能招聘 Agent

必须保留：

- 创建或选择一个招聘任务。
- 输入或加载岗位要求和简历样例。
- 输出候选人匹配分析或建议。
- 展示一张“工作流节点图”或流程图，用于替代 Dify 工作流总览。
- 保留 Dify 工作流证据：至少有工作流画布截图、节点说明、DSL 导出文件或等价配置截图。
- 报告中说明该模块是对 Dify 工作流思想的代码化实现，不能只说“没有 Dify”。

可以去掉或降级：

- OCR 简历解析。
- 批量候选人材料库。
- 复杂评分规则后台。
- 多轮人工复核。
- 复杂 Dify 生产部署、多模型路由、多环境发布。

MVP 判断：作业要求的是工作流智能体开发证据。当前系统可以用招聘 Agent 承担运行主链路，但报告里仍要有 Dify 工作流形态的证据，否则第三章会显得缺项。

### 4.4 智能问数 Agent

必须保留：

- 自然语言输入业务问题。
- 生成或展示 SQL。
- 返回查询结果表格。
- 最好有一个简单图表。
- 报告中提供数据模型、宽表 SQL 或简化版宽表设计。
- 准备 6-8 个固定演示问题。
- 保留飞书/企业微信入口证据：应用配置截图、机器人对话截图、或本地桥接服务收到消息并返回结果的截图。
- 保留 Dify/MCP 链路说明：至少在架构图中体现“飞书/企微 -> Dify/Agent -> SQL/MCP -> MySQL -> 结果返回”。

可以去掉或降级：

- 完整 `shop_db` 大数据量导入。
- 复杂图表配置器。
- 生产级飞书长连接稳定性、多群聊支持、CardKit 流式细节。
- 生产级 MCP 服务治理。
- 生产级 SQL 风控。

MVP 判断：智能问数的核心是 NL2SQL 和结果解释，但飞书/企微是作业里的展示入口，不能完全砍。可以降级为“最小入口 + 截图证据”，不做生产级稳定性。

### 4.5 飞书/企业微信桥接层

必须保留：

- 一个明确的外部协作入口，优先飞书，因为课件目录包含 `feishu-to-dify` 示例工程。
- API 配置中体现飞书 App ID/App Secret 或 Dify API Key 的配置位置。
- 至少一张飞书机器人配置截图或对话截图。
- 如果真实飞书联调暂时不稳定，保留本地模拟事件接口和日志截图，报告中说明真实联调的配置步骤。

可以去掉或降级：

- 多租户飞书应用管理。
- 多实例长连接。
- 群聊复杂 @ 解析。
- CardKit 流式卡片的精细更新。
- 图片、文件、语音消息。

MVP 判断：飞书/企微要保留“入口感”和“端到端证据”，但不承担所有复杂消息能力。

## 5. 建议从 MVP 中移除的高成本功能

| 功能 | 当前问题/成本 | 是否影响作业效果 | MVP 处理 |
| --- | --- | --- | --- |
| 生产级 Dify 运行时 | 需要部署、配置模型、导出 DSL、调节点 | 中等 | 保留最小工作流证据，不把完整 Dify 作为所有模块运行依赖 |
| 生产级飞书/企微端到端 | 需要外部平台账号、长连接/回调、权限和签名校验 | 中等 | 保留最小入口和截图证据，砍多群聊、流式卡片、复杂消息 |
| Qdrant/BGE/Reranker | 依赖多、调试慢、对法律 Demo 不是必须 | 低 | 去掉，法律咨询先走 LLM 或固定知识样例 |
| OCR 简历/材料解析 | 文件上传、识别服务、异常处理复杂 | 低 | 去掉，使用文本样例 |
| 完整 RBAC/多租户 | 数据模型和 UI 成本高 | 低 | 只保留本地账号/当前账号 API Key |
| 高风险审核/审计后台 | 报告中不是主评分点 | 低 | 降为截图或说明，不做主链路 |
| 生产级 Docker/Nginx | 运维成本高 | 低 | 保留本地启动脚本和健康检查 |
| SSE 流式细节 | 易出现兼容和中断问题 | 低 | 可用普通请求返回，流式作为加分项 |

## 6. 目前需要重点关注的异常

这些异常会影响 MVP 演示，应优先排查：

- API 配置页曾出现 500，需要验证三个 Agent 的配置接口都能读写。
- 三个 Agent Tab 切换后配置列表必须跟随变化，否则会影响“统一 API 配置中心”展示。
- 如果没有真实 API Key，三个 Agent 需要有可演示的降级路径，不能直接报错中断。
- 飞书/企微入口不能只写在文档里，至少要有配置页、桥接接口、日志或对话截图之一。
- Dify 工作流不能只口头说明，至少要有工作流图、节点截图或 DSL 证据之一。
- 智能招聘模块如果依赖 OCR 或文件解析，应改为文本样例优先。
- 智能问数模块如果依赖完整 `shop_db_export.sql`，应准备轻量示例数据或固定演示查询，避免大 SQL 导入成为阻塞。
- 部分历史文档或终端输出存在编码乱码，报告编写时应重新整理为清晰中文。

## 7. MVP 实施阶段

### MVP-0：冻结演示范围

目标：确定只演示三条主链路，不再扩展企业级功能。

交付物：

- 三个模块的演示脚本。
- 需要截图的页面清单。
- 需要写入报告的架构图清单。
- 每个模块的降级策略。
- Dify、飞书/企微、MCP 三个作业显性点的截图证据清单。

建议耗时：0.5 天。

### MVP-1：法律咨询主链路

目标：完成法律咨询模块的可运行演示。

验收标准：

- 能打开法律咨询页面。
- 能提交一个法律问题。
- 能看到回答。
- 能看到历史记录。
- API Key 未配置时提示清晰，或使用演示模式。

建议耗时：1 天。

### MVP-2：智能招聘工作流案例

目标：把招聘 Agent 包装成 Dify 工作流智能体案例。

验收标准：

- 能创建或选择招聘任务。
- 能输入岗位和候选人材料。
- 能输出匹配分析。
- 报告中有工作流节点图。
- 有 Dify 工作流截图、DSL 或等价配置证据。
- 页面截图能证明运行结果。

建议耗时：1 天。

### MVP-3：智能问数主链路

目标：完成自然语言问数到 SQL 和结果展示。

验收标准：

- 有轻量可用的数据表或宽表。
- 准备 6-8 个固定业务问题。
- 每个问题能展示 SQL 和查询结果。
- 至少一个问题有图表或可视化结果。
- SQL 安全规则在报告中说明。
- 有飞书/企微配置或对话截图。
- 架构图体现 Dify/MCP/MySQL 链路。

建议耗时：1-1.5 天。

### MVP-4：报告与证据包

目标：把系统成果转成作业可提交材料。

交付物：

- 实训报告正文。
- 三模块架构图。
- 三模块运行截图。
- 核心代码清单。
- 问题记录表。
- 项目运行说明。
- GitHub 或本地仓库说明。

建议耗时：1 天。

## 8. 最小验收清单

MVP 完成时，应满足以下条件：

- 本地能打开统一工作台。
- 左侧导航能进入法律咨询、智能招聘、智能问数三个模块。
- 三个 Agent 至少各有一条成功演示链路。
- API 配置中心能展示三个 Agent 的依赖项，并支持编辑保存或明确演示模式。
- Dify 工作流有截图/DSL/节点说明证据。
- 飞书/企微有配置截图、对话截图或桥接日志证据。
- 智能问数体现 MySQL、宽表、NL2SQL、SQL 执行结果。
- 报告中能解释当前技术栈为什么比课程示例更完整。
- 报告中不承诺尚未完成的 OCR、RAG、生产级多租户和生产级运维能力。
- 所有截图和代码说明能覆盖报告大纲要求。

## 9. 推荐汇报口径

建议在报告和演示中这样定位项目：

> 本项目基于《大数据应用实训》的三模块要求，将课程中的 AI 法律咨询、Dify 工作流智能体、智能问数系统整合为一个统一的企业智能体工作台。系统采用 Vue 3 + FastAPI + MySQL 架构，对原课程示例进行了工程化升级。为保证实训交付质量，MVP 演示范围聚焦于三个核心链路：法律咨询、招聘工作流分析、自然语言问数。

这样可以把“没有完全照搬 Dify/飞书/Node 示例”解释为工程化升级，而不是偏题。

## 10. 下一步建议

下一步不要继续扩展新功能。应先执行 MVP-0：

- 固定三个模块的演示问题和样例数据。
- 检查 API 配置页后端是否完全可用。
- 检查三个 Agent 的最小运行链路。
- 把非 MVP 页面从演示路径中移除或弱化。
- 开始收集报告截图和问题记录。

确认本计划后，再进入具体修复阶段。

### 11.2 应该保留并做出特色的内容

当前系统已经比课程标准更工程化，特色不应该做成“更多后台页面”，而应该做成“课程标准 + 统一平台升级”：

| 特色点 | 怎么做 | 展示价值 |
| --- | --- | --- |
| 统一智能体工作台 | 三个模块统一入口、统一导航、统一 API 配置 | 比课程分散 Demo 更完整 |
| 每账号独立 API Key | API 配置中心按账号保存 DeepSeek、Dify、飞书等 Key | 符合你提出的“每个账号独有”需求 |
| 三 Agent 健康状态 | 展示法律、招聘、问数服务是否可运行 | 现场演示前可快速证明系统在线 |
| 智能招聘作为 Dify 综合案例 | 用招聘任务串起开始、参数提取、条件分支、代码评分、模板报告等节点 | 正好对应 Dify 案例索引里的“智能招聘助手 Agent” |
| 智能问数宽表 + SQL 安全 | 展示宽表字段、生成 SQL、仅 SELECT、安全拦截 | 比单纯聊天更有技术含量 |
| 飞书桥接证据 | 复用 `feishu-to-dify` 的长连接/桥接/日志设计 | 贴合课程“飞书 + Dify”路线 |
| 8 个标准问题演示面板 | 在 Web 端列出 T1-T8，一键发问或复制到飞书 | 让老师一眼看到课程验收点都覆盖 |

| 法律分类后台 | 隐藏或只保留前台分类展示 | 分类可以作为静态选项，不必做后台 CRUD |
| 法律知识材料后台 | 隐藏 | 课程法律模块重点是 DeepSeek 问答，不强制法律 RAG 知识库 |
| 法律 Prompt 版本后台 | 隐藏 | Prompt 可放报告和配置，不需要后台版本治理 |
| 法律高风险审核 | 隐藏 | 企业级合规功能，作业不要求 |
| 招聘候选材料库 | 隐藏 | Dify 综合案例可以用文本简历，不必做文件库 |
| 招聘评分规则后台 | 隐藏 | 匹配分数可以在流程里固定规则，报告解释即可 |
| 招聘审计后台 | 隐藏 | 作业要求工作流结果，不要求审计系统 |
| 数据 SQL 审计后台 | 保留轻量截图，别做重后台 | 智能问数需要 SQL 安全，但不需要完整审计运营台 |
| 个人偏好设置 | 隐藏 | 与作业无关 |
| 复杂运维/Nginx/Docker 生产部署 | 降级为启动说明 | 课程有 Docker/Dify 环境，但项目演示重心不是生产运维 |
| Qdrant/BGE/Reranker | 暂不作为必跑依赖 | 法律模块不靠 RAG 也能完成作业；RAG 可写扩展 |
| OCR 简历解析 | 暂不做 | 招聘案例用文本简历即可覆盖 Dify 参数提取与评分 |
| CardKit 流式卡片精细更新 | 降级 | 飞书入口要保留，但打字机式流式卡片不是 MVP 必须 |
| 多群聊、多实例长连接 | 不做 | `feishu-to-dify` 文档本身也提示长连接生产限制，MVP 单实例即可 |

### 11.4 最终 MVP 形态

最终 MVP 不应是“删到只剩三个页面”，而应是：

1. **统一工作台**：登录后看到三个课程模块和 API 配置中心。
2. **法律咨询**：一条完整 DeepSeek 法律问答链路，含历史和截图。
3. **Dify/招聘工作流**：招聘助手作为综合案例，保留 Dify 节点图/DSL/运行结果。
4. **智能问数**：飞书或模拟飞书入口、Dify/Agent 编排、MCP/SQL 执行、MySQL 宽表、8 个问题验证。
5. **特色展示**：每账号独立 API Key、8 个测试问题面板、SQL 安全拦截、宽表设计说明。

这样砍完后项目仍然完整，并且比课程基础版更有特色：不是简单复刻课件，而是把课程三段内容统一成一个可演示的多智能体工作台。
